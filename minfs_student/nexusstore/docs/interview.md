# NexusStore：按实际代码准备面试

入门和口述练习先看 [面试准备简明主文档](../../面试准备-简明主文档.md)。本文保留较细的代码对应关系，供追问时查阅。

这份材料只解释 `nexusstore/` 的小文件存储原型。根目录早期设计和模拟 QA 中的 PD、RocksDB、Region 分裂、Lease Read、零拷贝以及 QPS 数字，不代表这里已经实现或测得的能力。项目完成时间、个人参与程度和性能结果，按自己的实际情况表达。

## 先把项目讲清楚

可以用下面的结构介绍，先理解代码，再改成自己的话：

> 我做了一个 Java 17、Maven 的三节点小文件存储原型。客户端通过 HTTP 上传、下载、删除文件，节点间使用 Netty 长连接异步 RPC。
>
> 文件 key 通过带虚拟节点的一致性哈希环路由到四个固定逻辑分片，每个分片对应一个独立 Raft 组。三个进程都保存全部四个分片的副本，可以观察不同分片各自选主、复制和恢复。
>
> 实现重点是领导者选举、日志复制、多数派提交、持久化恢复，以及请求自动转发到分片 leader。为了把强一致读做得容易解释，GET 也作为日志命令提交，得到多数派确认后再返回结果。
>
> 故障脚本会停止目标分片的 leader，验证已确认写入仍能读取、新写入恢复；再停止第二个节点，验证剩余单节点的读写都返回 503；最后恢复节点并检查日志追赶。Nacos 是可选的注册发现集成，本地演示不依赖它。
>
> 这个版本定位是可读、可验证的学习原型，单文件上限 1 MiB。已实现日志快照、压缩和落后副本分块恢复，没有做生产级吞吐承诺或在线扩容。

## 和简历怎么对应

| 简历中的方向 | 这里可以拿出来讲的代码和实验 | 表达边界 |
| --- | --- | --- |
| SpringCloud、Nacos 微服务治理 | Spring Boot HTTP 入口、Spring Cloud DiscoveryClient、可选 Nacos profile、Actuator 健康端点 | 本项目是同一种服务的三节点部署；不会为了微服务数量拆出订单、支付等无关服务 |
| 自动故障转移 | 分片 Raft 重新选主；服务端根据 leader 提示和固定 peer 重试转发 | Nacos 不决定 Raft 谁是 leader；客户端直连的 HTTP 进程死掉后，客户端仍需改连存活节点 |
| Netty 高性能异步通信 | 长连接复用、请求 ID 匹配 CompletableFuture、超时清理、长度字段拆包、在途请求限制 | 使用 Netty 不等于已证明“高性能”；JSON 编解码、磁盘同步和 Raft 串行化也会限制吞吐 |
| 一致性哈希分片与负载分散 | key → 虚拟节点环 → `s0..s3`；每个分片独立的 leader 和日志 | 是逻辑分片，不是三台机器存三份互不相同的数据；全部节点都保存全部分片，不能据此声称容量水平扩展 |
| Raft 与 CP | 三副本多数派、落盘、冲突日志处理、选举、故障恢复；无多数派时强读写返回 503 | 目标是每个分片内的线性一致操作；没有跨分片事务，也不保证拜占庭容错 |
| Redis、MySQL、订单限流 | 本次按需求省略 | 不能把这个 demo 没有的组件说成它的实际实现；其他项目的经历单独说明 |

## 现场演示：运行一次比背一段更有用

在 `nexusstore` 目录打开 PowerShell，准备 JDK 17 和 Maven。

```powershell
# 首次构建并启动三个隐藏后台 Java 进程。
./scripts/start-cluster.ps1 -Build

# 二进制文件上传、下载 SHA-256 校验、删除、404。
./scripts/smoke-test.ps1

# 查看各节点本地状态；这不是强一致文件读取接口。
Invoke-RestMethod http://127.0.0.1:8081/api/cluster | ConvertTo-Json -Depth 6
Invoke-RestMethod http://127.0.0.1:8082/api/cluster | ConvertTo-Json -Depth 6
Invoke-RestMethod http://127.0.0.1:8083/api/cluster | ConvertTo-Json -Depth 6

# 自动完成杀 leader、失去多数派、恢复与追日志实验。
./scripts/failover-test.ps1

# 停 follower、覆写并压缩、安装快照、再切主验证恢复结果。
./scripts/snapshot-test.ps1

# 结束演示；保留数据，下一次启动可恢复。
./scripts/stop-cluster.ps1
```

如果本机执行策略阻止运行脚本，可以仅对这次 PowerShell 进程设置 `Set-ExecutionPolicy -Scope Process Bypass`，然后重跑命令。脚本通过 PID、进程启动时间、Java 命令行中的本项目路径和节点 ID 校验所有权，不会按“所有 Java 进程”批量停止。它们不会清空数据目录。

HTTP 端口是 `8081/8082/8083`，Netty 端口是 `9091/9092/9093`。标准输出、错误输出与 PID 记录在 `.runtime/`；持久化数据在 `data/node1..node3/`。启动脚本可重复运行；重新构建前先停止集群。故障脚本会自动补齐尚未启动的节点，结束后保留三个运行中的节点。

要演示 Nacos，先按项目 README 启动并配置本机 Nacos，再从停止状态运行 `./scripts/start-cluster.ps1 -Nacos`。该开关启用 Spring profile，不会安装或启动 Nacos。故障重启会保留节点记录中的 Nacos 配置。注册发现不改变 Raft 三节点投票名单。

演示时解释每一步的判据：

1. 先根据 key 查询 `/api/route`，找到目标 `s0..s3`，再去 `/api/cluster` 找该分片 `role=LEADER` 的节点。一个节点可能是某个分片的 leader，同时是其他分片的 follower。
2. 停一个进程后还有 `2/3` 副本，等待选主后读已确认的数据，并验证新写入。故障期间会暂时不可用，不能声称“零中断”。
3. 停第二个进程后只剩 `1/3` 副本。强读、写都应返回 HTTP 503。健康端点仍可能是 UP，因为“进程活着”不等于“存在可提交请求的多数派”。
4. 恢复节点后看目标分片的 `lastApplied` 是否追到故障前已确认的提交位置，再比较文件哈希。仅仅通过恢复节点的 HTTP 入口读成功，不足以证明它的本地副本追赶完成，因为请求可能被转发。

脚本验证的是同机多个进程的宕机与恢复。它没有模拟真实网络分区、磁盘损坏、机器断电或跨机时钟/调度条件；不要把一次通过等同于完整的一致性验证。

## 面试追问与回答要点

### 1. 为什么用了 Raft 还要 Nacos？

它们回答不同的问题。Nacos 提供服务实例注册和发现信息；Raft 判断哪个副本能领导某个复制组、日志能否提交。Nacos 中某节点暂时不可见，不能直接把它从投票名单移除，否则两个网络分区可能各自重新计算多数派。

这里 Raft 成员来自固定配置，Nacos 只接受与已配置 peer 一致的发现结果，并保留固定地址作为回退。服务注册与领导者选举是两条独立路径。

### 2. 一致性哈希和 Raft 如何配合？

先用稳定哈希确定 key 属于哪个逻辑分片，再将请求交给该分片的 leader。哈希解决“操作归哪个组”，Raft 解决“组内副本如何按相同顺序提交操作”。

默认四个分片、每个分片 64 个虚拟节点。虚拟节点改善 key 的分布，但不自动消除热点 key；一个热点 key 始终属于一个分片。增加分片数还涉及数据迁移，本项目会校验持久化拓扑，避免带旧数据静默修改哈希映射。

### 3. 写入什么时候才算成功？

leader 追加日志，将日志复制到副本，满足 Raft 的多数派和当前任期提交规则后推进 `commitIndex`，按顺序应用到状态机，再向客户端返回成功。TCP 发送成功、follower 收到请求、leader 自己写完磁盘，都不能单独代表集群提交成功。

要能结合实现说明三个值：`lastLogIndex` 是已有日志的末尾，`commitIndex` 是已提交的边界，`lastApplied` 是状态机实际应用到的位置。某节点日志末尾更大，不能据此认定多出来的内容已经提交。

### 4. leader 宕机为什么不会丢掉已确认的写入？

多数派之间有交集，但只说“有交集”还不完整：选举时还要检查候选人的日志新旧程度，按末条日志任期和索引比较；投票和任期也需要持久化。符合这些约束的后继 leader 才能保留已提交日志。

未确认写入可能已经提交，也可能仍未提交、以后被覆盖。接口返回 503 或网络超时表示没有拿到成功结果，不表示操作必定未发生。

### 5. 旧 leader 恢复后会怎样？

它收到更高任期的消息后退回 follower。新 leader 根据日志前缀匹配复制缺失部分，必要时覆盖冲突的未提交后缀；已经提交的日志不能任意截断。恢复完成要看提交和应用进度，不能仅看进程重新启动。

还要区分“旧 leader 自认为还是 leader”和“它能提交新请求”：网络隔离中的旧 leader 可能暂时没得知更高任期，但没有多数派就不能确认新的强读写。

### 6. 为什么 GET 也需要多数派？

如果旧 leader 被隔离后直接从本地返回数据，而另一侧已经选出新 leader 并成功写入，就会读到过期值。本项目把 GET 排进 Raft 日志，在该日志提交和应用的位置读取状态机，因此能和同分片写入明确排序。

代价是每次 GET 都增加日志和磁盘操作；读取不存在的 key 返回 404 也经过这条路径。这是为了简化正确性推理而做的选择。生产优化通常会考虑 ReadIndex 或有严谨前提的 lease read，本版本没有实现它们。

### 7. 这里的 CP 到底是什么意思？

发生网络分区或多数副本不可达时，为了维持强一致语义，无法取得多数派的一侧拒绝文件操作。`2/3` 的一侧在选主后可以继续服务，`1/3` 的一侧不能仅凭本地数据提供强读。

CAP 里的 C 指线性一致性，A 也不是“正常运行时 HTTP 很快”。本项目用宕机实验观察多数派不足时的行为，并没有通过该实验证明所有网络分区交错下都正确。

### 8. Netty 怎么解决拆包、请求对应和超时？

TCP 是字节流，协议使用四字节长度前缀加 UTF-8 JSON，长度解码器处理半包和粘包，并限制帧大小。请求携带 ID，客户端用在途表把响应对应到 CompletableFuture；连接断开和超时都要异常完成请求并清理记录。

客户端复用长连接，限制在途请求数量，并检查写缓冲区水位，避免无限排队。网络事件线程不能等待磁盘或等待自己发送的 RPC；Raft 状态推进交给对应组的执行路径。本版本仍有 JSON 拷贝和文件内容的序列化，不宣称零拷贝。

### 9. 重试会不会重复执行？

先明确超时结果不确定。PUT/DELETE 支持客户端提供 `X-Request-Id`，同一次业务操作重试时应保留这个 ID，而不是每次生成新 ID；同一个 ID 也不能拿去代表另一次写入。服务端内部转发重试会保留原命令 ID。

不要只说“同 key 覆盖写所以幂等”：一次旧写在后续新写完成后被重新执行，仍然可能把新内容覆盖掉。理解实现中请求去重的保存范围与生命周期，再讨论能提供多强的重试保证。去重并不等于跨多个文件的事务。

### 10. 为什么不用成熟 Raft 库？

这次要展示能理解和调试选举、日志前缀匹配、提交边界、恢复以及一致性读，所以保留了可读的手写实现。手写原型适合学习，不能直接等同于经过长期故障注入验证的生产实现。

进入实际服务时会评估成熟 Raft 实现、异步快照和分段 WAL、成员变更、流控、批量复制、鉴权、资源隔离和可观测性。先说本版本做了什么以及如何验证，再讨论这些后续工作。

### 11. 快照之后为什么还需要日志索引和去重表？

快照替换已应用前缀，不会让逻辑日志重新编号。必须保存 lastIncludedIndex/lastIncludedTerm，让下一条日志的前缀匹配、投票新旧比较和重启回放仍使用相同边界。未提交日志不能因为要压缩就丢弃。

去重表保证旧写重试不会覆盖后来的新值。快照保留 requestId、命令指纹和首次执行结果，去掉历史 PUT 内容。如果 Follower 需要的日志已被压缩，Leader 按 256 KiB 块发送快照，最终校验和落盘后才能确认安装。读恢复节点的 HTTP 接口可能发生转发，所以演示还要看它自身 snapshotIndex/lastApplied，并让它参与新的多数派。更多细节见 [快照讲解](snapshots.md)。

## 接下来按什么顺序读代码

1. `nexus-server` 的 `FileController`：从一次 PUT/GET 请求看到命令和 HTTP 响应。
2. `NodeRuntime` 和 `nexus-common` 的 `ConsistentHashRing`：定位分片、寻找 leader、处理转发和重试。
3. `nexus-common` 的 `RpcClient`、`RpcServer`、`RpcFrames`：跟踪一个 RPC 的请求 ID、连接、Future 和响应。
4. `nexus-raft`：画出 follower → candidate → leader 的转换，跟踪投票、AppendEntries、持久化、提交和 apply。
5. 对照测试和 `scripts/failover-test.ps1`，解释每个断言要防止什么错误。能亲自修改一个小场景并预测结果，比背完整套 QA 更能支撑面试追问。

不要在未测量的情况下给出 QPS、P99 或优化倍数。若以后压测，记录机器配置、JDK、文件大小、并发数、请求类型、是否每条日志同步落盘、运行时长、成功率、错误分布和延迟分位数。当前 GET 仍写日志，快照制作和安装有延迟成本；永久去重表也有容量限制，快照不能当作无限运行能力的证明。
