# minFS 技术设计文档

> 一个"麻雀虽小五脏俱全"的分布式文件系统（DFS）教学/面试向实现。
> 本文基于对 `metaServer` / `dataServer` / `easyClient` 三个模块全部源码的通读整理而成，
> 既描述**设计意图**，也标注**实现现状**与**已知缺陷**，便于面试时讲清楚"为什么这么做"和"如果重做会怎么改"。

---

## 0. 一句话概述

minFS 是一个**元数据与数据分离**的分布式文件系统：

- `metaServer` 负责「命名空间 + 文件 → 副本位置」的映射（对标 HDFS NameNode / GFS Master）；
- `dataServer` 负责真实字节的落盘与读取（对标 HDFS DataNode / GFS ChunkServer）；
- `easyClient` 是轻量级 SDK，屏蔽寻址与网络细节，暴露类 `java.io` 的 `create/open/mkdir/delete` API；
- ZooKeeper 同时充当**注册中心、选主协调者、元数据存储**三重角色。

## 2. 总体架构

### 2.1 逻辑架构

```
                 ┌──────────────────────────────────────────┐
                 │              Zookeeper                    │
                 │  /meta/services/{master,slave}   选主/寻址  │
                 │  /meta/metadata/<filePath>       文件元数据 │
                 │  /data/data_<port>               DS 注册   │
                 └───────▲──────────▲───────────▲────────────┘
                         │          │           │
         1. 查 master    │          │ 写元数据   │ 注册临时节点
            地址         │          │           │ + 定时上报容量
                    ┌────┴─────┐   │       ┌────┴──────────────┐
                    │   SDK    │   │       │                   │
   ┌────────┐       │EFileSystem│  │       │   dataServer 集群  │
   │ 业务方  │──────▶│FSOutput  │  │       │  (无状态, 可横向扩容)│
   └────────┘  HTTP │FSInput   │  │       │  ds1  ds2  ds3 ... │
                    └────┬─────┘  │       └────▲─────▲─────▲───┘
                         │        │            │     │     │
                         │ HTTP   │    ┌───────┘     │     └──────┐
                         ▼        ▼    │  3 副本写入  │            │
                    ┌──────────────────┴──┐                       │
                    │     metaServer      │───────────────────────┘
                    │  主备(Master/Slave) │   create/mkdir/write/delete/read
                    │  + 选点 + fsck 自愈 │
                    └────────────────────┘
```

### 2.2 模块职责

| 模块 | 角色 | 核心类 | 职责 |
| --- | --- | --- | --- |
| `metaServer` | 控制面 | `MetaController` / `MetaService` / `SaveService` / `RegistService` / `FsckServices` | 命名空间管理、元数据持久化、副本选点、副本自愈、主备选举 |
| `dataServer` | 数据面 | `DataController` / `DataService` / `RegistryService` / `FileUtils` | 本地磁盘读写、目录/文件创建删除、向 ZK 注册并心跳上报容量 |
| `easyClient` | 接入层 | `EFileSystem` / `FSOutputStream` / `FSInputStream` / `ZkUtil` / `ClusterInfo` | 服务发现、HTTP 封装、类 `java.io` 流式 API |

设计上 **dataServer 单节点无状态，可横向扩容**；**metaServer 主备模式运行**（当前主备只做选主，未做数据同步——见 §8）。

### 2.3 与成熟系统的对照（面试常问"你这是抄谁"）

| 概念 | HDFS | GFS | minFS |
| --- | --- | --- | --- |
| 元数据节点 | NameNode | Master | metaServer |
| 数据节点 | DataNode | ChunkServer | dataServer |
| 分块 | Block（128MB） | Chunk（64MB） | **未分块**，整文件单块 |
| 副本数 | 3（可配） | 3 | 3（硬编码） |
| 元数据存储 | 内存 + EditLog/FsImage | 内存 + 日志 | ZooKeeper |
| 写入链路 | Client → DN 流水线 | Client → CS 流水线 | Client → MS → 3×DS（**串行扇出**） |
| 副本修复 | 心跳 + Replication Monitor | re-replication | `FsckServices` 定时巡检 |

## 3. 数据模型

### 3.1 文件元数据 `StatInfo`

```java
public class StatInfo {
    String path;                 // 全局唯一逻辑路径，如 /a/b.txt，同时作为 ZK 节点 id
    long   size;                 // 文件大小（字节）
    long   mtime;                // 创建/修改时间（毫秒时间戳）
    FileType type;               // Unknown/Volume/File/Directory
    List<ReplicaData> replicaData; // 副本位置列表（设计目标 3 份）
}
```

```java
public class ReplicaData {
    String id;      // 该 dataServer 在 ZK 上的注册节点路径，如 /data_9000
    String dsNode;  // "ip:port"，实际访问地址
    String path;    // 该副本在 DS 本地磁盘上的绝对路径
}
```

**设计要点**：`ReplicaData` 把「逻辑路径 → 物理位置」彻底解耦。文件迁移、副本重建只需改 `replicaData`，`path` 不变，客户端无感。

### 3.2 DataNode 注册信息

`dataServer` 启动及每 10s 向 ZK 写入 CSV 格式（`RegistryService`）：

```
host, port, fileTotal, capacity, useCapacity, rack, zone
 0     1       2          3          4          5     6
```

- `capacity` 来自配置 `application.capacity`（默认 1GB），`useCapacity` 由 `FileUtils` 递归统计本地 `data_<port>` 目录得到；
- `rack` / `zone` 是**为机架感知预留**的字段（当前选点算法尚未使用，见 §7.3）。

### 3.3 ZooKeeper 目录树

```
/
├── meta/                                 ← metaServer 的 Curator namespace
│   ├── services/
│   │   ├── master   [EPHEMERAL] "ip,port"   主节点，Client 直接读它寻址
│   │   └── slave    [EPHEMERAL] "ip,port"   备节点
│   └── metadata/                         ← 命名空间树，与文件路径一一对应
│       ├── wdag/
│       │   └── www/
│       │       └── test1.txt  [PERSISTENT] → StatInfo JSON
│       └── test2.txt          [PERSISTENT] → StatInfo JSON
└── data/                                 ← dataServer 的 Curator namespace
    ├── data_9000   [EPHEMERAL] "ip,port,fileTotal,capacity,useCapacity,rack,zone"
    ├── data_9001   [EPHEMERAL] ...
    └── data_9002   [EPHEMERAL] ...
```

**关键设计**：

1. **用 ZK 的树形结构天然表达目录层级**。`listFileStats` 直接 `getChildren("/metadata" + path)` 即可列出目录内容，不需要额外维护 children 列表。
2. **Namespace 隔离**：metaServer 配置 `zookeeper.namespace=meta`，dataServer 配置 `data`，两者共用一套 ZK 但互不干扰，节点路径自动带上前缀。
3. `MetaService` 为了读取 `dataServer` 的注册信息，单独 `new` 了一个**无 namespace** 的 Curator 客户端（`MetaService#run`），直接访问根路径 `/data`。这是一个"跨命名空间访问"的技巧，也是面试可以主动讲的细节。

## 4. 服务注册与高可用

### 4.1 dataServer 注册 + 心跳

```java
// RegistryService#run (ApplicationRunner)
registryToCenter();  // 创建 EPHEMERAL 节点 /data_<port> 并写入容量信息
createDataDir();     // 本地创建 data_<port>/ 作为数据根目录
updateData();        // 首次上报

@Scheduled(cron = "*/10 * * * * ?")
public void updateData() { ... }   // 每 10s 刷新容量
```

- 使用 **EPHEMERAL 临时节点**：进程崩溃 / 会话超时后节点自动消失，实现最朴素的**故障发现**（无独立心跳协议，依赖 ZK Session）。
- 每次写文件成功后也会主动调用 `updateData()`，让容量变化尽快可见。
- 本地存储根目录为 **`${user.dir}/data_${server.port}`**——即"一个端口一个数据目录"，方便单机起多个 DS 模拟集群（这也是 `workpublish` 一键脚本的做法）。

### 4.2 metaServer 主备选举

`RegistService` 采用 **ZK 唯一临时节点抢占**实现选主：

```
启动 → try create EPHEMERAL /services/master
       ├─ 成功 → 我是 Master，写入 "ip,port"
       └─ 失败 → 抢占失败，创建 /services/slave，成为备机
监听 → PathChildrenCache("/services") 监听 CHILD_REMOVED
       └─ Master 节点消失 → sleep 3s（防网络抖动/防脑裂）→ 删除 slave 节点 → 抢建 master
```

**设计意图**：
- 3s 等待是对**网络抖动**的朴素防护，避免 Master 因一次 GC/网络闪断就被误判下线导致频繁切主；
- 客户端只读 `master` 节点，切主后客户端需要重新发现（当前 SDK 只读一次，见 §9）。

### 4.3 客户端寻址

```java
// ZkUtil#postCons (@PostConstruct)
String s = new String(client.getData().forPath("/meta/services/master"));
metaPath = split[0] + ":" + split[1];   // "ip:port"
```

`metaPath` 是 `static` 变量，所有 `EFileSystem` 方法拼接 `http://${metaPath}/xxx` 使用。
同时 `TreeCache` 监听逻辑已实现（`zkWatch`），**但调用处被注释掉了**，所以目前是"启动期一次性寻址"。

## 5. 核心流程

### 5.1 创建文件 `create(path)`

```
Client                metaServer                      ZooKeeper         dataServer ×3
  │  POST /create?path  │                                 │                   │
  ├────────────────────▶│ pickDataServer()                │                   │
  │                     ├──── getChildren("/data") ──────▶│                   │
  │                     │◀─── [data_9000, 9001, 9002] ────┤                   │
  │                     │ 按 useCapacity 升序排序，取前 3   │                   │
  │                     │ POST /create?path  ────────────────────────────────▶│
  │                     │◀─── 本地绝对路径 ───────────────────────────────────┤
  │                     │ 组装 ReplicaData{id, dsNode, path}                   │
  │                     │ saveService.metatoZk(StatInfo) ─▶│                   │
  │◀─── 200 OK ─────────┤                                 │                   │
```

`MetaController#createFile` 会**逐级创建父目录**（`for i in 1..len-2: mkdir`），保证 `/a/b/c.txt` 写入时 `/a`、`/a/b` 已存在。

若某个 DS 调用失败，`MetaService#createFile` 仅打印日志并跳过 → **降级为 2 副本或 1 副本**，后续由 fsck 补齐（这是"可用性优先"的取舍，面试可展开）。

### 5.2 写入 `write(path, bytes)`

`FSOutputStream.write(byte[])` → `POST http://master/write?path=xxx`（body 为原始字节）
→ `MetaService#commitWrite`：

1. 从 ZK 读取 `StatInfo`；
2. **串行**遍历 `replicaData`，逐个 `POST http://dsNode/write?path=xxx`（`APPLICATION_OCTET_STREAM`）；
3. 更新 `size = bytes.length`、`mtime`，回写 ZK。

`dataServer` 侧 `DataService#write` 用 `new FileOutputStream(file)`（**非 append**）落盘，然后 `updateData()` 刷新容量。

### 5.3 读取 `read(path)`

`metaServer#read` 从 `replicaData` 中**随机挑一个副本**（`Random.nextInt`），转发 `POST /read?path=`，把 DS 返回的 `InputStreamResource` 原样透传给客户端，包装成 `FSInputStream`。

### 5.4 删除 `delete(path)`

**先删数据、再删元数据**：遍历副本调 `POST /delete?path=` → 成功后 `client.delete().deletingChildrenIfNeeded().forPath("/metadata" + path)`。
`dataServer` 侧对目录做了保护：目录非空时拒绝删除。

### 5.5 目录列举 `listFileStats(path)`

`getChildren("/metadata" + path)` → 逐个 `getNode` 反序列化为 `StatInfo` → 返回列表。
`path="/"` 时特殊处理为空串。

### 5.6 副本自愈 `FsckServices`（`@Scheduled(fixedRate = 60s)`）

```
全量遍历 /metadata 下所有节点
   └─ replicaData.size() < 3 ?
        ├─ File      → recoveryFile()：在新 DS 上 create → 从现有副本 read → write 回填 → 补 ReplicaData
        └─ Directory → recoveryDir() ：在新 DS 上 mkdir  → 补 ReplicaData
   └─ 回写 ZK 元数据
```

选新 DS 时会用 `threeDataMap` 与已有副本做**去重**，且要求集群节点数 ≥ 3 才启动修复。
同时 `MetaService#zkWatch` 的 `NODE_REMOVED` 分支会在 DS 掉线瞬间**主动摘除**所有元数据里指向该 DS 的副本，把"副本数不足"的信息快速暴露给 fsck。

## 6. 关键设计决策（面试重点讲这部分）

### 6.1 元数据与数据分离

- 控制面（metaServer）只处理**小、结构化、高频随机读写**的元数据；数据面（dataServer）只处理**大、流式、顺序读写**的字节。
- 好处：两者可独立扩容；数据面无状态、故障域隔离；客户端拿到副本位置后理论上可直连 DS（HDFS 就是这么做的）。
- 代价：多一次网络跳转。**minFS 当前写入仍由 metaServer 中转**，这是明显的吞吐瓶颈（见 §9）。

### 6.2 三副本策略

- 副本数硬编码为 3，遵循"**先降级写入、后异步补齐**"的思路：写入时尽力写 3 份，失败不阻断请求；由 fsck 每分钟巡检补齐。
- 副本粒度 = **整文件**，没有分块（Block/Chunk）。这是与 HDFS/GFS 最大的差距：大文件无法并行读写、无法做流水线复制、单文件不能超过单盘容量。

### 6.3 副本选点（负载均衡）

```java
// MetaService#updateDS + pickDataServer
lists = new ArrayList<>(dataMap.entrySet());
Collections.sort(lists, (o1, o2) ->
    Integer.parseInt(o1.getValue().get(4)) - Integer.parseInt(o2.getValue().get(4)));
// → 按 useCapacity 升序，取前 3
```

即 **"选当前已用容量最小的 3 个节点"**，属于最简单的 **Least-Used 贪心**。

**已知不足**（非常适合面试时主动说）：
- 排序字段是**绝对已用容量**而非**使用率**（`useCapacity / capacity`），异构磁盘场景下会偏向大容量机器；
- 未使用已上报的 `rack` / `zone` 字段，**三副本可能全落在同一机架/可用区**，机架断电即数据丢失。源码 `DataService#write` 的 todo 里明确写了 `az rack->zone 的方式选取`，说明作者有这个规划但没实现；
- 未考虑写入热点、磁盘 IO 负载、节点权重。

### 6.4 心跳与容量感知

- 复用 **ZK Session + EPHEMERAL 节点**做存活探测（10s 定时 `setData` 刷新容量，既是心跳也是指标上报）；
- metaServer 用 **TreeCache** 监听 `/data` 的全量子节点事件，实时感知上下线。

### 6.5 元数据持久化选型

用 ZK 存元数据的**利**：天然树形、天然 Watch、顺序一致性、自带版本号（可用 CAS 做乐观锁）。
**弊**：ZK 单节点数据上限 1MB、**全量元数据受单机内存限制**、QPS 有限。
生产级做法：内存 + WAL（EditLog）+ 定期 Checkpoint（FsImage），或换成 etcd/RocksDB/TiKV。这是面试必答题。

### 6.6 SDK 设计

- 继承 `InputStream` / `OutputStream`，让业务方零学习成本（**面向接口复用 JDK 生态**）；
- 服务地址通过 ZK 动态获取，业务方只配置 ZK 地址；
- 提供 `getClusterInfo()` 运维视角 API，可查看主从 metaServer 与所有 DS 的容量水位；
- 预留了基于 `httpclient5` 的连接池 + 重试封装（`HttpClientUtil` / `HttpClientConfig`），但实际调用仍用 `new RestTemplate()`（未接管）。

## 7. 一致性、可用性与容错

| 维度 | 现状 | 说明 |
| --- | --- | --- |
| 元数据一致性 | **单 Master 写入 + ZK 保证** | ZK 的写是原子的、顺序一致的，避免了多主写冲突 |
| 数据一致性 | **最终一致** | 三副本串行写，中途失败会产生副本不一致，靠 fsck 收敛 |
| 写原子性 | **无** | 没有 WAL、没有租约（Lease）、没有临时文件 + rename，写一半宕机会留下脏数据 |
| 并发写同一文件 | **无保护** | 无锁、无租约、无版本号 CAS，后写覆盖先写 |
| 读可用性 | **随机副本 + 无故障转移** | 选中宕机副本会直接抛异常，不会自动换副本重试 |
| metaServer HA | **有选主，无数据同步** | 元数据在 ZK 上所以备机可读；但 `threeDataMap` 等内存状态不共享，切主后需要重新 pickDataServer |
| dataServer 故障 | **自动摘除 + 异步补齐** | Watch 摘除副本 → fsck 重建 |

## 8. 已识别问题与改进方向

> 这一节是面试的"加分项"：能主动指出自己项目的不足并给出方案，比只讲优点更有说服力。

| # | 问题 | 位置 | 改进方案 |
| --- | --- | --- | --- |
| 1 | **写入全量经过 metaServer 中转**，控制面成为数据瓶颈 | `MetaService#commitWrite` | 改为 HDFS 式：Client 向 MS 申请副本位置 → **Client 直连 DS 流水线写入** → 完成后向 MS 提交（类似两阶段提交） |
| 2 | **未分块**，大文件无法并行、单文件受单盘限制 | 全局 | 引入 Block（64/128MB）；元数据改为 `file → [blockId...] → [replicas...]`；支持并行读、流水线写 |
| 3 | **write 是整文件覆盖**，`offset/length` 参数定义但未实现 | `DataService#write` | 用 `RandomAccessFile` + `FileChannel.write(buf, position)` 实现随机写；引入 `append` 语义 |
| 4 | **选点无机架感知**，三副本可能同机架 | `MetaService#updateDS` | 按 `zone → rack → node` 三级打散（参考 HDFS BlockPlacementPolicyDefault） |
| 5 | **选点按绝对容量**而非使用率 | 同上 | 改为 `useCapacity / capacity` 排序，或引入加权打分（容量 + IO + 连接数） |
| 6 | **静态容器非线程安全**：`dataMap` / `threeDataMap` / `lists` 均为 `static`，多线程写会 `ConcurrentModificationException`；且并发创建会互相覆盖 `threeDataMap` | `MetaService` | 改为实例字段 + `ConcurrentHashMap`；`pickDataServer` 结果作为方法返回值传递而非共享状态；选点加分布式锁或按 path 分段锁 |
| 7 | **下线的 DS 不会从 `dataMap` 移除**，可能仍被选中 | `MetaService#zkWatch` | `NODE_REMOVED` 时同步 `dataMap.remove(path)` |
| 8 | **选主简陋**：slave 节点路径固定，多备机会冲突；所有节点同时抢主造成**惊群**；无 fencing token，旧 Master 假死后可能双写 | `RegistService` | 改用 Curator `LeaderLatch` / `LeaderSelector`（顺序临时节点，天然公平队列）；或引入 epoch/fencing token |
| 9 | **主备无状态同步**：`threeDataMap` 等内存状态不共享 | `RegistService` / `MetaService` | 状态全部下沉到 ZK/共享存储，或备机切主后强制重建 |
| 10 | **`SaveService` 每次调用都 `new ServiceDiscovery` 且从不 close**，存在连接/线程泄漏；`discovery` 还是共享字段被反复覆盖 | `SaveService` | 复用单例 Curator 客户端，直接用 `client.setData()` / `getData()` 读写 JSON，去掉 `curator-x-discovery` 这层不必要的抽象 |
| 11 | **每次 RPC 都 `new RestTemplate()`**，无连接池、无超时、无重试 | 全局 | 注入单例 `RestTemplate` + `PoolingHttpClientConnectionManager`；设置 connect/read timeout；失败副本自动 failover |
| 12 | **读无故障转移**，随机选中坏副本直接失败 | `MetaController#read` | 按 rack/zone 就近优先 + 失败自动切下一个副本 |
| 13 | **fsck 是全量扫描 + 60s 周期**，元数据量大时 ZK 读压力与修复延迟都不可接受 | `FsckServices` | 改为事件驱动（DS 下线即触发该 DS 上副本的补齐）+ 按目录分片扫描 + 限速 |
| 14 | **`fsck` 循环条件写成 `while (count > 0 \|\| iterator.hasNext())`**，应为 `&&`，会导致迭代器越界 | `recoveryFile` / `recoveryDir` | 修正为 `count > 0 && iterator.hasNext()` |
| 15 | 大量 `catch (Exception) { log.info(...) }` **吞异常**，且 `getNode` 失败后直接 `statInfo.getReplicaData()` 会 NPE | `MetaService#delete/commitWrite` | 统一异常体系，区分「可重试」「需降级」「致命」；关键路径做空值校验 |
| 16 | **路径未做规范化和安全校验**，`../` 可穿越；`path` 拼接进 URL 未 encode | 全局 | 统一 `Path.normalize()` + 白名单校验 + `URLEncoder` |
| 17 | **无鉴权、无多租户**（`fileSystem` header 定义了但未使用） | Controller | 引入 token + ACL，支持多 `fileSystem` 命名空间隔离 |
| 18 | **元数据存 ZK 容量受限** | `SaveService` | 迁移到 RocksDB/etcd/分布式 KV，内存维护 + WAL 持久化 |
| 19 | 硬编码：`10.0.0.201:2181`、`127.0.0.1:2181`、副本数 3 | `EFileSystem#getClusterInfo` / `ZkUtil` | 外置为配置项 |
| 20 | 写盘未 `fsync`，宕机可能丢数据 | `DataService#write` | `FileChannel.force(true)`，或引入 WAL |

## 9. 面试高频问答速记

**Q：为什么元数据和数据要分离？**
A：访问特征完全不同——元数据小、随机、要求强一致；数据大、流式、要求高吞吐。分离后可独立扩缩容、独立优化存储引擎，数据面还能做成无状态的。

**Q：三副本怎么选节点？**
A：从 ZK 读取所有 DS 的已用容量，升序排序取前 3（Least-Used）。进阶：应该按 zone→rack→node 三级打散 + 使用率排序 + 权重打分。

**Q：写完一份副本失败了怎么办？**
A：minFS 选择"可用性优先"——跳过失败节点继续写，先返回成功，副本数不足由 fsck 异步补齐。对比 HDFS 的 pipeline：HDFS 会把失败节点剔除后继续 pipeline，最后在 `complete` 阶段校验副本数并触发复制。

**Q：怎么保证 Master 只有一个？**
A：利用 ZK 临时节点的**唯一性**（同名节点只能创建一次）+ **会话失效自动删除**。更标准的做法是用 Curator `LeaderLatch`（顺序临时节点排队）。

**Q：Master 挂了怎么办？**
A：`PathChildrenCache` 监听到 `/services/master` 被删除 → 等待 3s（防抖动）→ 删除自己的 slave 节点 → 抢建 master。客户端下次请求时重新从 ZK 读 master 地址完成切换。

**Q：怎么防止脑裂？**
A：当前只靠 3s 等待做了弱防护，**严格来说没有防住**。生产需要 fencing token / epoch：Master 每次写入携带递增 epoch，存储层拒绝小于当前 epoch 的写入。

**Q：元数据为什么用 ZK？有什么问题？**
A：好处是树形天然映射目录、自带 Watch 和版本、写操作顺序一致。问题是单节点 1MB 上限、总量受内存限制、QPS 有限。生产应该用 内存 + EditLog(WAL) + FsImage(Checkpoint)，或者 etcd / RocksDB。

**Q：和 HDFS 最大的差距是什么？**
A：三点——① 没有分块，整文件单块；② 写入没有走 Client→DS 流水线，而是 metaServer 中转；③ 没有租约/租约续约机制和完整的写一致性协议（HDFS 有 lease + pipeline + ack 反压）。

**Q：如果要你重构，第一件事做什么？**
A：先把数据链路从"metaServer 中转"改成"Client 直连 DS 流水线写"，这是吞吐的决定性因素；同时引入 Block 分块（分块是并行读、流水线写、副本打散的前提）。

## 10. 演进路线（如果继续做）

1. **分块（Block）**：元数据从 `file → replicas` 升级为 `file → block[] → replicas[]`，打开并行读、流水线写、大文件支持的空间。
2. **写入流水线化**：Client 向 MS 申请租约与副本位置 → 直连 DS 链式写 → ack 反向回传 → Client 向 MS 提交 → MS 校验副本数。
3. **一致性协议补齐**：租约（Lease）+ 版本号 CAS + 写前日志（WAL）+ `fsync`，实现"写失败不留脏数据"。
4. **机架感知选点**：`zone → rack → node` 三级放置策略，副本数可配（3 / EC 纠删码）。
5. **元数据引擎替换**：ZK 只保留"服务发现 + 选主"，元数据迁到 RocksDB/etcd，支持百万级 inode 与快照。
6. **可观测性**：接入 Micrometer + Prometheus，暴露 QPS、延迟 P99、副本健康度、容量水位；`fsck` 结果告警。
7. **多租户与安全**：`fileSystem` 命名空间落地 + 鉴权 + 配额（Quota）。

## 12. 启动方式（回忆用）

```bash
# 1. 启动 ZooKeeper
# 2. 打 easyClient-1.0.jar 供业务方依赖
mvn clean package
# 3. 依次启动
java -jar metaServer.jar --server.port=8000
java -jar dataServer.jar --server.port=9000 --az.rack=rack1 --az.zone=zone1
java -jar dataServer.jar --server.port=9001 --az.rack=rack2 --az.zone=zone1
java -jar dataServer.jar --server.port=9002 --az.rack=rack1 --az.zone=zone2
```

> 至少需要 3 个 dataServer，否则 fsck 会因 `dataMap.size() < 3` 直接跳过修复。
