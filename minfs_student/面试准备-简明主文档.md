## 项目介绍

### 30 秒版：先把这段说顺

> 这是一个 Java 实现的三节点小文件存储原型，支持上传、下载和删除。文件先通过一致性哈希找到所属分片，再由 Raft 协调这个分片的三个副本，至少两份确认后才返回写入成功。节点之间通过 Netty 通信，Nacos 用于服务注册发现。它主要用来验证选主、数据复制和故障恢复：停掉一个节点可以继续服务，只剩一个节点时拒绝读写，优先保证一致性。

### 展开到约一分钟：面试官有兴趣再补

> 原型用 Spring Boot 提供 HTTP 接口，Spring Cloud 接入 Nacos。为了控制复杂度，限定为三个节点、四个固定分片，单文件最大 1 MiB。
>
> 每个分片都有独立的 Raft Leader 和日志；任意存活节点收到请求后，可以转发给对应 Leader。Leader 把操作写成日志、复制到多数副本，再按顺序执行。读取也经过多数派确认，避免隔离的旧 Leader 返回旧数据。
>
> 后续补了日志快照和落后副本恢复。验证时会停 Leader、恢复副本、制造只剩单节点的情况，再检查文件内容。这个版本侧重把一致性流程讲清楚，尚没有可对外承诺的吞吐提升数字。

### 技术栈各自干什么：不用混着背

| 技术 | 本项目里的职责 |
|---|---|
| Java、Spring Boot | 实现服务，提供上传、下载、删除等 HTTP 接口 |
| Spring Cloud、Nacos | 接入服务注册发现，获取服务实例信息 |
| 一致性哈希 | 根据文件 key 找到固定逻辑分片 |
| Netty | 传输节点间的文件转发、投票、日志和快照消息 |
| Raft | 决定谁是 Leader、哪些操作可以提交、副本怎样恢复一致 |
| Redis、MySQL | 对应简历中的订单限流和缓存场景；当前文件 demo 未接入 |

**只背一句职责划分：哈希决定找哪个组，Raft决定组内怎么确认，Netty负责传消息，Nacos提供实例信息。**

## 先理解数据怎么走

### 文件、分片、副本：三个不同的东西

这里的文件可以看成一条 `key → 文件字节`：例如 `/photo/a.jpg → 一段图片内容`。key 是逻辑名称，不是服务器磁盘目录。

| 概念 | 直白解释 | 本 demo 的例子 |
|---|---|---|
| 文件 | 用户保存的一份内容 | a.jpg、b.txt |
| 分片（shard） | 把不同文件分成几个组管理 | a.jpg 属于 s0，b.txt 属于 s2 |
| 副本（replica） | 同一组数据在不同节点保留的拷贝 | s0 在 node1、node2、node3 各有一份 |
| Leader | 负责安排本组操作顺序的副本 | s0 当前由 node1 负责 |
| Follower | 接收日志、参与投票和复制的副本 | s0 的 node2、node3 |

分片不是把 a.jpg 切成三段，副本也不是三个节点各保存不同文件。**本 demo 每个文件归一个分片，而每个分片又在三台节点上各保存一份。**

这里提供的是小文件 key/value 操作，没有目录遍历、文件追加、挂载成本地盘等完整文件系统能力。面试称“小文件存储原型”更准确。

### Multi-Raft：同一批机器上，运行多组 Raft

先只看 s0：三个副本通过 Raft 选出一个 Leader，维护一份共同的操作顺序。这是一组 Raft。

再加上 s1、s2、s3，每组重复同样的选举和复制流程，就是这里的 Multi-Raft。它没有要求你另学一种选举算法；一个进程同时参与多个组。这个含义也见 [TiKV 的 Multi-Raft 说明](https://tikv.org/deep-dive/scalability/multi-raft/)。

下面是**便于理解的角色示例**，实际 Leader 随选举变化，并不保证平均分配：

| 逻辑分片 / Raft 组 | node1 进程 | node2 进程 | node3 进程 |
|---|---|---|---|
| s0 | Leader | Follower | Follower |
| s1 | Follower | Leader | Follower |
| s2 | Follower | Follower | Leader |
| s3 | Leader | Follower | Follower |

**横着看**：一组有三个副本、一个 Leader。**竖着看**：一个进程保存四组副本，可以同时是某组的 Leader、另一组的 Follower。每组的任期、日志、提交进度独立；相同的日志编号在不同组里没有关联。

为什么分多组？不同组可以独立排序、处理请求，也为以后分散负载提供基础。但本 demo 四组都复制到同样三个节点，**每台都保存全部文件，有效容量没有变成三倍**。不同组仍共享进程和磁盘资源，也没有跨组事务。

**可以这样答：**“Multi-Raft 就是按分片运行多组独立的 Raft。每组还是正常的选举和多数派复制；一台机器可以参加多个组，也能在不同组扮演不同角色。”

### 一次上传：把这一条流程走通

假设 `a.txt` 属于 s0，s0 的 Leader 是 node2，而客户端请求发给了 node1：

```text
客户端 PUT a.txt
    → node1 的 HTTP 接口
    → 一致性哈希算出 s0
    → 通过 Netty 转发给 s0 的 Leader：node2
    → node2 写本地日志，并向 node1、node3 复制
    → 自己 + 至少一个 Follower 的日志落盘确认
    → 达到提交条件，按顺序执行写文件操作
    → 返回成功；暂时落后的第三个副本继续追赶
```

**这里多数派是 2/3，包含 Leader 自己。不是必须等两个 Follower 全部确认。** 也不是每次都临时挑一台最空闲的机器写入，key 已经决定了分片。

### 日志、提交、状态机：用 Java 的 Map 理解

这里的 Raft 日志是可重放的操作记录，不是 `log.info()` 打印的调试文本。例如：

```text
第 1 条：PUT a.txt = v1
第 2 条：PUT a.txt = v2
第 3 条：DELETE a.txt
```

状态机就是按顺序执行这些命令的程序。在本 demo 中，可以理解成对 `Map<文件key, 文件字节>` 做 put/get/remove，并维护写请求去重记录。各副本从相同状态开始，按相同顺序执行相同的确定性命令，就能得到相同结果。

| 阶段 / 指标 | 你需要理解的意思 |
|---|---|
| 追加日志 / lastLogIndex | 我收到并保存到第几条；尾部可能还没提交 |
| 提交 / commitIndex | 已经确定可执行到第几条，不应再被后继 Leader 推翻 |
| 应用 / lastApplied | 本地 Map 已经实际执行到第几条 |

正常情况下 `lastApplied ≤ commitIndex ≤ lastLogIndex`。**“收到了”不等于“已提交”，“已提交”也不要求所有副本此刻都已执行完。**

## 项目常见问答

### 1. 为什么需要 Raft？TCP 可靠传输还不够吗？

**可以这样答：**TCP 解决两个端点之间怎样传字节。它不能决定三个节点里谁负责写，也不能决定 Leader 写到一半宕机后保留哪次操作。Raft 用统一的操作顺序、选举和多数派确认，让一组副本对已经提交的结果达成一致。

**再问一层：**RPC 是把请求发给另一台机器并接收结果。Netty 是实现本项目 RPC 的工具；Raft 是使用这些消息运行的一套共识规则。

### 2. Raft 怎么选主？

**可以这样答：**节点有 Follower、Candidate、Leader 三种角色。Leader 定期发心跳；Follower 一段时间收不到心跳，就提高任期，转成 Candidate，先投自己，再向其他节点要票。三节点拿到两票就成为 Leader。如果没选出来，就在新的超时后重试。超时时间带随机性，减少大家同时发起选举。

**再问一层：**投票还会检查候选人的日志是否足够新，不是“谁先来就投谁”。同一任期最多支持一个候选人，任期和投票要保存到磁盘，重启不能忘记已经投过票。

选举和基本安全规则可对照 [Raft 论文 Figure 2](https://raft.github.io/raft.pdf)；面试准备阶段先掌握上面的过程，不要求背证明。

### 3. term 是什么？为什么不会选出两个主？

**可以这样答：**term 是单调增加的任期编号，可以理解成“第几届”，用来识别过时的 Leader 和消息。同一任期里，每个节点最多投给一个候选人，而任意两个多数派都至少有一个共同节点，所以同一组同一任期不会合法选出两个 Leader。

**再问一层：**不同任期里，新旧节点可能暂时都认为自己是 Leader；旧的那一个拿不到多数派，就不能确认新操作。看到更高任期后，旧 Leader 会退回 Follower。

### 4. 为什么三个节点要两个确认？为什么不用两个节点？

**可以这样答：**多数派要求超过一半。三个节点需要两个确认，允许坏一个还继续服务。两个节点的多数派也是两个，坏一个就不能继续写，所以要容忍一个节点故障，三节点更合适。

**再问一层：**五节点需要三个确认，可以容忍两个故障；副本更多也会增加存储和复制成本，不是越多越好。

### 5. 写成功后 Leader 马上挂了，会丢数据吗？

**可以这样答：**在这个原型约定的节点进程故障场景里，已返回成功的写入经过了多数派落盘。之后的选举还要求候选人日志足够新，结合多数派有交集，新的 Leader 会保留已提交操作。只写到一台、还没确认的尾部，则可能被覆盖。

**再问一层：**“日志足够新”先比较最后一条日志的任期，再比较编号，不能只看谁的日志条数多。整机断电、所有磁盘损坏不在本 demo 的验证承诺内。

### 6. 读取为什么也要经过多数派？读本地不是更快吗？

**可以这样答：**旧 Leader 被隔离后可能还存着旧值；另一侧却已经选出新 Leader 并完成新写入。如果它直接读本地，就会把旧数据返回给客户端。本 demo 为了让规则简单，把 GET 也排进 Raft 日志，提交后再读取，这样读写能在同一分片内排出一致的顺序。

**再问一层：**代价是读也要复制和落盘。不是所有 Raft 系统都必须这么读，ReadIndex 是可进一步优化的方向，这里没有实现。

### 7. CAP 是什么？你的 CP 怎么体现？

先把三个字母说准：**C** 是线性一致性，可以先理解为“操作看起来像作用在一份按顺序更新的数据上”；**A** 要求非故障节点收到请求后最终完成符合该服务语义的响应；**P** 是网络可能把节点隔开，系统要面对这种通信故障。返回一个错误码不等于满足 CAP 的可用性。网络分区存在时，无法同时无条件满足 C 和 A，见 [Gilbert 与 Lynch 的 CAP 论文](https://www.cs.princeton.edu/courses/archive/spr22/cos418/papers/cap.pdf)。

**可以这样答：**如果三节点分成能互通的两台和孤立的一台，两台这一侧在选主后可以继续提交；孤立的一台即使还活着，也拒绝新的强一致读写。我们牺牲这部分可用性来保护一致性，这就是本项目的 CP 取舍。

**再问一层：**不要背成“CAP 随便选两个”。网络分区是一种需要处理的故障条件；CP 也不表示正常时一直不可用。这里的强一致性针对同一分片内的操作，没有跨分片原子事务。

**小例子：**写入 `a=v2` 已成功返回，之后才发起的强一致读取不能返回 v1；如果读写本来就是同时发生的，就需要按它们的实际排序理解结果。

### 8. 宕机节点恢复后，怎样追上别人？

**可以这样答：**它先从本地持久化状态恢复，再和当前 Leader 对齐。运行时文件值在内存 Map 中，磁盘上的快照和日志用于重建它，不需要依赖 MySQL。缺少的日志由 Leader 补给它；冲突但尚未提交的尾部会被替换。如果它落后太久，需要的旧日志已经压缩，就先安装快照，再追快照之后的日志。

**再问一层：**程序启动成功只说明进程起来了。要判断数据追平，应看本地提交、应用位置和文件内容；通过它的 HTTP 入口读成功，也可能只是转发给了别的节点。

### 9. 请求超时是不是就没写成功？重试会不会执行两次？

**可以这样答：**超时只能说明客户端没拿到确认。可能没提交，也可能已经提交但响应丢了。因此同一次写入重试时保留同一个请求 ID。状态机记住已处理的 ID 和结果，重复请求返回原结果，避免把旧操作执行两次。

**再问一层：**例如 A 写 v1，B 后来写 v2，再重试 A 时不能把 v2 覆盖回 v1。所以“覆盖写天然幂等”并不足以解释乱序重试。本 demo 把去重结果也保存在快照里。

### 10. 快照是什么？为什么已经有日志还需要它？

**可以这样答：**日志记录“做过哪些操作”，快照保存“执行到某个位置时的数据结果”。如果把 a 从 v1 改到 v100，恢复时没必要永远从第一条重放，可以保存当前 a=v100，以及快照对应的日志编号和任期，再保留后面的日志。这样减少历史日志占用，也能加快落后副本恢复。

**再问一层：**快照只能替换已经应用的前缀，没提交的尾部不能随便删除。日志编号继续增长，不会做完快照就从 1 重新开始。Raft 快照用于恢复副本状态，不等于独立备份，也不等于你简历中的 pprof 健康采样。

### 11. 有了 Raft，为什么还需要 Nacos？节点下线后怎么办？

**可以这样答：**Nacos 提供服务注册和发现，Raft 管的是本组谁能领导、操作能否提交。它们职责不同。Nacos 发现一个实例下线，不代表可以把 Raft 投票名单里这个节点直接删掉，否则每个分区自己缩小多数派人数就会出错。

**再问一层：**本 demo 的三个成员固定配置，Nacos 可选启用，发现不可用时仍有固定地址。内部请求会重试、转发给新 Leader；如果客户端直连的 HTTP 进程已经死了，客户端仍需要换一个入口，当前没有统一网关自动替它完成这一步。

### 12. 一致性哈希能解决热点吗？节点挂了要不要重新映射？

**可以这样答：**虚拟节点能改善 key 分布不均，但同一个热点 key 仍映射到同一分片，不会自动拆散它的流量。本 demo 哈希的是固定分片；物理节点挂掉后，分片内换 Leader，文件仍归原分片，不会因为临时故障就重建哈希环。

**再问一层：**新增分片后，一致性哈希只能减少需要改变映射的数据范围，数据迁移仍要另做。这里没有在线扩容和迁移，不能直接改配置当成扩容完成。

### 13. 这是微服务项目吗？三个 Maven 模块就是三个微服务吗？

**可以这样答：**当前 demo 是同一种存储服务的三节点部署，用 Spring Cloud 接入服务发现。common、raft、server 是代码模块，只有 server 是启动入口。Maven 模块数量不等于微服务数量；简历里原来其他服务的拆分情况，需要结合当时实际系统介绍。

### 14. 项目的难点和性能怎么讲？

**可以这样答：**技术难点主要是把成功响应和多数派提交对应起来：不能把“收到日志”当成“提交成功”，也不能让孤立旧 Leader 返回旧值。我可以用停主、只剩单节点和恢复副本的流程解释这些判断。

**再问一层：**Netty 的异步通信有助于复用连接和减少等待线程，但整体吞吐还受磁盘同步、序列化和日志处理限制。当前使用 JSON、文件内容进日志、整体状态文件重写，重点是可读和可验证，没有测过就不报 QPS 或提升倍数。回答“我遇到的困难”时，选自己实际调试并理解的一件事展开。

### 15. 你怎么验证它？

**可以这样答：**先验证上传、跨节点下载内容一致、删除后不存在；再停掉 Leader，检查剩余两节点选主后旧数据可读、新写能成功；只剩一个节点时检查读写被拒绝；恢复后检查副本追平。快照还会专门验证落后副本安装后能参与新的多数派。

**再问一层：**仓库当前有 44 项通过的自动化测试和本机三进程演示记录。它们是限定场景的功能验证，不是生产规模压测或全部故障情况的证明。自己跑过并看懂一次，再把观察过程作为个人演示经历讲。详情见 [验证记录](nexusstore/docs/validation.md)。

### 有人追到 Raft 细节：只备这一小段

“Leader 复制时会带前一条日志的编号和任期，Follower 用它检查前缀是否匹配；不匹配就回退找共同前缀。Leader 不能只凭旧任期日志存在于多数节点就直接宣布它提交，要通过当前任期条目的提交来带动前面的日志。新 Leader 的空操作可以建立这个当前任期提交点。”

这段知道意思即可，暂时不展开证明、成员变更、PreVote 或 Multi-Paxos。基础问题回答时也不必主动引出这些词。

## Go补课

你熟悉 JVM，可以借助“执行任务、栈和堆、可达性、GC、排查工具”这些已有概念理解 Go，但两种运行时的实现不能一一照搬。

### 1. goroutine 是什么？和线程有什么区别？

**可以这样答：**goroutine 是 Go 运行时管理的轻量并发执行单元，写 `go f()` 就能让函数并发执行。很多 goroutine 可以复用一组操作系统线程，初始栈较小、能按需调整，适合大量等待网络请求的任务。但最终执行仍需要操作系统线程和 CPU，也要限制任务数量。[Go FAQ](https://go.dev/doc/faq#goroutines)

**再问一层：**Java 平台线程通常对应操作系统线程；Java 虚拟线程也由运行时调度，思路有相近之处，但具体实现与 goroutine 不同。不能笼统地说“Java 一个任务一定占一个系统线程”。参见 [Java 虚拟线程说明](https://openjdk.org/jeps/444)。

### 2. GMP 是什么？GOMAXPROCS 限制什么？

**可以这样答：**G 是 goroutine，表示待执行的任务；M 是操作系统线程，负责真正执行；P 是执行 Go 代码所需的调度资源，可以先理解成“执行资格”。M 拿到 P，才能执行普通 Go 代码。GOMAXPROCS 决定 P 的数量，限制同时执行 Go 代码的并行度，不限制 goroutine 总数，也不等于系统线程总数。[Go 运行时说明](https://go.dev/src/runtime/HACKING)

**小例子：**假设有 1,000 个 goroutine，GOMAXPROCS 设置为 4，不能理解成 1,000 个任务同时计算；可以有很多任务等待，普通 Go 代码的并行执行受这四份调度资源限制。

**再问一层：**网络等待通常可以挂起 G、腾出执行资源；阻塞系统调用可能占住 M，运行时会安排其他线程继续执行。先知道这个区别，不要求背调度队列和抢占源码。

### 3. 并发和并行有什么区别？开得越多越快吗？

**可以这样答：**并发是多个任务在同一时间段内推进，可以交替，也可以同时；并行强调同一时刻真正在多个核上执行。一个核也能并发处理多个请求，比如一个请求等网络时处理另一个。网络等待多的任务可以适当增加并发；纯计算任务受 CPU 限制，goroutine 过多反而增加调度和内存开销。

**再问一层：**并发上限也要考虑数据库连接池和下游承受能力。可以用固定数量的 worker 或信号量限制在途任务，不是看到 `go` 很便宜就无限创建。

### 4. 怎么等任务完成？channel、WaitGroup 和锁分别干什么？

**可以这样答：**等一组任务完成用 WaitGroup；任务之间传数据或结果可用 channel；多个任务读写同一份状态可用 Mutex。WaitGroup 只负责等待，不自动保护共享变量。channel 是带类型的通信通道；无缓冲通道需要收发双方配合，有缓冲通道满了也会阻塞。[Go 同步工具](https://pkg.go.dev/sync)、[channel 说明](https://go.dev/ref/spec#Channel_types)

| 场景 | 最先考虑的工具 |
|---|---|
| 并发查三个接口，等它们都结束 | WaitGroup；结果和错误需要另外收集 |
| 一个任务生产数据，另一个处理 | channel |
| 多个任务修改共享 map | Mutex，或重新设计数据所有权 |
| 请求超时后通知这些任务退出 | context |

**再问一层：**普通 map 不能无保护地并发读写；不能靠 sleep 猜任务结束，也不能以为用了 channel 就没有数据竞争。已有代码可以用 `go test -race` 辅助检查竞争。

### 5. context 怎么取消任务？什么是 goroutine 泄漏？

**可以这样答：**context 用来传递截止时间和取消通知，比如请求超时后通知下游停止。任务要检查 `ctx.Done()`，或者调用支持 context 的接口，收到通知后主动返回。它不会强行杀死 goroutine。如果任务一直等没人接收的 channel、没有超时的网络调用，又没有退出路径，就可能一直占着资源，形成泄漏。[context 官方文档](https://pkg.go.dev/context)

**再问一层：**要明确谁启动、谁取消、谁等待任务退出。创建带超时或取消能力的 context 后及时调用 cancel；channel 等待可以用 select 同时监听业务结果和取消信号。context 也能传请求范围的值，但不适合当作任意业务参数容器。

### 6. Go 的栈、堆和逃逸怎么理解？

**可以这样答：**goroutine 有自己的栈，常用来放函数调用和局部数据；需要更长生命周期的数据可能放到堆上，由 GC 管理。编译器通过逃逸分析判断对象怎样分配，所以局部变量不一定在栈上，`new` 也不等于一定分配到堆上。Go 可以安全返回局部变量的地址，编译器会安排合适的存储。[Go 栈与堆 FAQ](https://go.dev/doc/faq#stack_or_heap)

**再问一层：**逃逸会影响分配和 GC 开销，但具体结果受上下文、内联和编译器版本影响，不是看到取地址就断言一定逃逸。这里知道含义即可，暂不展开内存分配器源码。

### 7. Go GC 和 JVM GC 怎么对比？有 GC 为什么还会泄漏？

**可以这样答：**两者都会自动回收不再可达的对象。Go 标准运行时的 GC 大部分工作能和业务并发执行，但仍有暂停和 CPU 开销。不能把 JVM 中常见的年轻代、老年代和收集器参数直接套到 Go 上，具体实现要看版本。[Go GC 指南](https://go.dev/doc/gc-guide)

**再问一层：**没用的数据如果还被全局 map、无上限缓存或不退出的 goroutine 引用，GC 不会替业务判断它该删除，所以有 GC 仍可能内存泄漏。增加堆空间只能暂时缓解某些问题，不会解决持续积累。

### 8. 简历写了 pprof 和 OOM 排查，你具体看什么？

**可以这样答：**先区分 Go 程序报错退出，还是被系统或容器因内存不足杀掉，再看时间点附近的监控和系统记录。pprof 里，heap 看存活堆内存主要从哪里分配，goroutine 看任务数量和阻塞栈，CPU profile 看一段时间里 CPU 花在哪。把异常现场与之前的健康采样比较，判断对象是否持续积累、任务是否泄漏，或计算和 GC 开销是否上升。[pprof 官方文档](https://pkg.go.dev/runtime/pprof)

**再问一层：**Go heap 不等于进程实际驻留内存 RSS。堆不大而 RSS 很高时，还要查栈、运行时开销、原生内存或映射等来源。heap profile 是分配位置和统计，不等于 Java 完整 heap dump 的对象引用链；CPU 采样也不能直接说明任务为什么长时间等网络。

**对应你的守护模块经历：**OOM kill 可能以 SIGKILL 结束进程，没有机会依赖 panic/recover/defer 保存现场，所以平时保留健康采样、在异常阈值出现时尽早采集有意义。采集也需要限制频率和保留数量。这里的“健康快照”是诊断采样，与 Raft 快照不同；[Go 信号说明](https://pkg.go.dev/os/signal)明确 SIGKILL 无法捕获。

## Redis与多级缓存

这部分对应简历的订单限流、多级缓存和多实例定时任务。下面给的是可解释的设计方案；当前文件 demo 没有这些组件，具体历史实现用自己实际用过的版本回答。

### 1. Redis 在业务里可以做什么？为什么快？

**可以这样答：**Redis 可以缓存热点数据、保存共享会话、做计数、排行榜和限流。例如商品信息用缓存，访问次数用计数器，排行榜用有序集合。它主要访问内存，常用操作较轻，事件循环能处理很多连接；但慢命令、大 key 和长脚本仍会拖慢其他请求。[Redis 性能说明](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/)

**再问一层：**通常说 Redis 单线程，主要指常规命令执行；网络 I/O 和后台任务可能有其他线程。不要回答“Redis 完全只有一个线程”。

### 2. 多级缓存是什么？有了 Redis 为什么还要本地缓存？

**可以这样答：**可以用“本地缓存 → Redis → MySQL”理解。本地命中就直接返回，没有网络开销；本地没有再查多个应用共享的 Redis；两层都没有才查数据库并回填。这样既减少数据库查询，也能降低 Redis 的热点压力。代价是本地缓存占 JVM 内存，各应用又有自己的副本，更新时更难保持一致。[Redis 客户端缓存说明](https://redis.io/docs/latest/develop/clients/client-side-caching/)

**小例子：**十个应用实例反复查询同一份商品展示信息，如果各自在本地留一份短期缓存，大量请求就不用每次访问 Redis。Java 可以选择 Caffeine 实现本地缓存，但这是可选方案，不代表你的原项目已经用了它。

**再问一层：**适合读多写少、允许短暂陈旧的数据；本地缓存要限制容量和过期时间。库存展示可以缓存，最终库存扣减不能仅依据可能过期的展示缓存。

### 3. 更新数据库以后，缓存怎么办？

**可以这样答：**常见做法是数据库事务成功后删除缓存，下一次查询再从数据库加载，叫 Cache Aside。有本地缓存时，还要通知各实例删除本地副本，用过期时间兜底。但先更数据库再删缓存也不是强一致：删除可能失败，并发中的旧查询也可能晚一步把旧值写回。删除失败要重试，必要时通过可靠消息推进失效；核心正确性判断仍依赖数据库事务。[Redis Cache Aside 示例](https://redis.io/docs/latest/develop/use-cases/cache-aside/nodejs/)

**再问一层：**先删缓存再改数据库，可能让中间的请求读到旧数据库值并重新缓存；因此常见方案选择先更新数据库，但它也消除不了所有竞争。单纯延迟双删不能证明强一致；失效通知若会丢，不能只依赖通知而没有过期或其他恢复措施。

### 4. 穿透、击穿、雪崩怎么区分？

| 问题 | 发生了什么 | 最先想到的办法 |
|---|---|---|
| 穿透 | 老查根本不存在的数据，每次都到数据库 | 校验参数、短期缓存空结果，必要时布隆过滤器 |
| 击穿 | 一个热点 key 失效，大量请求同时回源 | 合并同 key 的加载请求，限制回源并发 |
| 雪崩 | 大量缓存同时失效，或 Redis 故障 | 打散过期时间、限流降级、保护数据库 |
| 热点 key | 即使缓存命中，一个 key 的流量仍特别大 | 本地缓存、请求合并，按业务评估拆分 |

**可以这样答：**“穿透是查不到也总来查，击穿是一个热点突然失效，雪崩是很多缓存一起失效。处理上分别考虑挡无效查询、合并加载、打散过期和限流。”

**再问一层：**布隆过滤器可以挡掉一定不存在的值，但判断“可能存在”时仍要查询；它也要跟着真实数据维护。一致性哈希的虚拟节点不能把同一个热点 key 自动变成多个 key。

### 5. 简历里的 Redis 令牌桶怎么解释？

**可以这样答：**桶容量决定允许多大的突发，补充速率决定长期放行速度。比如容量 20、每秒补 10 个令牌，满桶时可以立即通过 20 个请求；之后每秒恢复 10 个。Redis 保存剩余令牌和上次补充时间，每次请求按经过的时间算补充量，再判断是否够扣。多个服务实例共享同一个桶，才不会每台都额外放行一份额度。[Redis Java 令牌桶](https://redis.io/docs/latest/develop/use-cases/rate-limiter/java-jedis/)

```text
新令牌数 = min(桶容量, 原令牌数 + 经过的时间 × 补充速率)
足够本次消耗 → 扣减并放行
不够         → 拒绝，或由上层决定是否等待
```

**再问一层：**不必每隔一毫秒真的往 Redis 加令牌，请求到来时计算“本来应该补了多少”即可。桶按用户、接口还是整个系统共享，要先看业务限流目标。

### 6. 为什么要用 Lua？能直接 GET 再 SET 吗？

**可以这样答：**如果读取、判断和扣减分成多个请求，两个实例可能同时看到最后一个令牌，然后都放行。Lua 让这几个步骤在 Redis 中原子执行，避免中间被其他请求插入；令牌数和补充时间也一起保存。这保证的是这段 Redis 状态更新的原子性，不等于整个业务请求成为事务。

**再问一层，暂不必背实现：**拒绝时也要一致地处理补充后的状态；时间最好统一来源。桶过期后若初始化成满桶，过期时间就不能短到让没补满的桶提前重置。Redis Cluster 中，多 key 脚本还要求相关 key 在同一 slot。脚本应短小，避免阻塞其他请求。

### 7. 分布式锁怎么做？为什么有锁还要幂等？

**可以这样答：**Redis 的常见加锁写法是 `SET lock 唯一标识 NX PX 超时时间`，原子地完成“不存在才写”和设置过期。释放时用 Lua 先检查标识仍属于自己，再删除，防止误删后来别人拿到的锁。但租约过期后，原任务可能还在执行，新的任务又拿到了锁，所以还要用业务幂等或数据库约束防止重复生效。[Redis 分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

**对应简历的定时任务：**多个实例可能同时触发某个群的同一轮跟进，锁可减少重复执行；进一步可按“群 ID + 会话版本 + 轮次”识别同一次业务操作。分布式锁不自动保证外部消息严格只发送一次，持久化状态与发送之间的失败也要处理。简历没有注明锁的具体实现，是否用 Redis 应按实际情况回答。

### 8. Redis 宕机怎么办？怎么证明缓存有收益？

**可以这样答：**先设置短超时，避免请求一直等待；允许旧值的查询可暂时用本地缓存，同时限制回源并发，保护数据库。超出的请求要降级或拒绝，不能全打到数据库。Redis 还承担限流时，要预先确定故障策略：关键写接口可以保守拒绝，普通查询可以用本地限流兜底。

**再问一层：**看本地与 Redis 的命中率、数据库 QPS、响应延迟和错误率；没有测过就不报提升百分比。缓存系统通常允许短暂旧值，而本文件 demo 的 GET 选择强一致，两者针对的需求不同。

## Netty三问

### 1. Netty 是什么？为什么用它？

**可以这样答：**Netty 是 Java 网络通信框架，封装了连接、网络事件、缓冲区和编解码等工作，适合实现异步网络服务。本项目用它做节点之间的 RPC，传输投票、日志和文件请求。它不是注册中心，也不负责决定数据一致性。[Netty 官方指南](https://netty.io/wiki/user-guide-for-4.x.html)

### 2. NIO、异步通信怎么理解？

**可以这样答：**NIO 常见做法是让少量线程观察多个连接，有连接可以读写时再处理，不给每条连接都放一个线程一直等。异步则是发起操作后先返回，通过回调或 Future 接收完成结果。Java NIO 的非阻塞、多路复用和异步调用不是同一个概念，但可以组合使用。

**再问一层：**Netty 的网络事件线程不能长时间做磁盘操作或等待远程响应；本项目把 Raft 状态和持久化处理放到分片自己的执行线程里。

### 3. 半包粘包是什么？响应怎么对应请求？

**可以这样答：**TCP 只提供字节流，不保留应用消息边界。一条消息可能分几次读到，多条消息也可能一次读到。本项目在消息前加长度字段，收到完整长度才解析；同时给请求编号，把响应对应到等待中的 Future，超时或断连时清理它。

到这里即可。暂时不要求背 Netty 源码、零拷贝、内存池或复杂 Reactor 变体。

8. goroutine 由运行时调度，context 是取消通知，任务要自己响应退出。
9. 有 GC 也会泄漏；pprof 的 heap、goroutine、CPU 看的是不同问题。
10. 缓存通常容许短暂陈旧；令牌桶和锁的共享状态要原子处理，但不等于业务绝不会重复。
